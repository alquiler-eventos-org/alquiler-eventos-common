SECCION 1 - QUE PIDE LA ENTREGA 2
====================================================================

Cada integrante desarrolla UN microservicio independiente en Java +
Spring Boot. Los dos juntos forman el sistema integrado, conectados
a la MISMA base de datos remota PostgreSQL (Supabase) de la entrega 1.

1.1 ESTRUCTURA MINIMA DE DATOS (por microservicio)
- Al menos 1 entidad simple (sin relaciones complejas).
- Al menos 1 entidad con relacion muchos-a-muchos, gestionando
  correctamente su asociacion.
- Para entidades de otros dominios: usar las clases del JAR common
  de la entrega 1 SIN modificar su definicion.

   Como lo cumplimos:
   - Setrini:  entidad simple = Proveedor
               entidad M:N    = OrdenCompra <-> Equipo
               (la asociacion se gestiona via OrdenCompraDetalle)
   - Tobi:     entidad simple = Cliente
               entidad M:N    = OrdenAlquiler <-> Equipo
               (via OrdenAlquilerDetalle) + ChecklistItem

1.2 ARQUITECTURA Y CAPAS
- Patron estandar Spring: controller -> service -> repository (+ dto).
- IoC con @RestController, @Service, @Repository, etc.
- PROHIBIDO saltarse capas: el controller NUNCA llama a un
  repository directo; todo pasa por el service.
- Especializacion por entidad: cada clase trabaja UN solo tipo de
  entidad. Los servicios/repositorios de APOYO (ej. Equipo) no
  necesitan controller expuesto (la rubrica lo permite conversado
  en grupo; aqui queda documentado como se cumple).
- Jerarquia de clases para reutilizar codigo transversal:
  interfaz generica Mapper<E, D> implementada por todos los mappers.
- Entities y DTOs: usar las clases del JAR SIN modificarlas.
- Mapeo bidireccional DTO <-> Entity.
- Persistencia con Spring Data JPA.

1.3 OPERACIONES REST OBLIGATORIAS (verbos y codigos HTTP correctos)
- POST   crear                              -> 201 (400 si invalido)
- PUT    actualizar                         -> 200 (404/400 si corresponde)
- GET    /{id} obtener por id               -> 200 (404 si no existe)
- GET    listar CON PAGINACION OBLIGATORIA  -> 200
- GET    buscar con filtros + paginacion    -> 200
- DELETE borrado LOGICO (marcar inactivo)   -> 200 (404 si no existe)

1.4 REQUISITOS TECNICOS TRANSVERSALES
- Maven resuelve el JAR common como dependencia.
- TODO configurable (application.yml + variables de entorno).
- Manejo centralizado de excepciones (@RestControllerAdvice) con
  respuestas estandarizadas (DTO ApiError del JAR) y ocultamiento
  de errores tecnicos (nunca filtrar stacktrace al cliente).
- Logs en disco con SLF4J/Logback y niveles por capa:
  Controller: INFO  (solicitudes entrantes/salientes)
  Service:    INFO/DEBUG (pasos clave de la logica de negocio)
  Repository: DEBUG (consultas SQL importantes)
- Swagger/OpenAPI documentando todos los endpoints.
- Conexion obligatoria a la BD remota compartida (Supabase).

2.2 CAMBIOS NUEVOS PARA LA ENTREGA 2
a) pom.xml: classifier "exec" en spring-boot-maven-plugin.
   Ahora el JAR normal (alquiler-eventos-common-1.0.0-SNAPSHOT.jar)
   es la LIBRERIA que consumen los microservicios, y el ejecutable
   se publica aparte (-exec.jar). Sin esto los ms NO podian usar
   las clases del JAR.

b) Borrado logico de ordenes: se agrego ANULADA a los enums
   EstadoOrdenCompra y EstadoOrdenAlquiler. No requiere cambios en
   la BD (la columna estado es VARCHAR).

c) Borrado logico de maestros: campo nuevo "activo" (Boolean) en
   Proveedor y Cliente + changeSets Liquibase 17 y 18 que agregan
   la columna activo BOOLEAN NOT NULL DEFAULT TRUE a las tablas
   proveedores y clientes. Liquibase lo ejecuta solo al arrancar
   la app por primera vez.

d) Queries de busqueda con filtros + paginacion en los repos:
   - ProveedorRepository.buscar(nombre, email, contacto, pageable)
     (siempre excluye activo = false)
   - ClienteRepository.buscar(nombre, apellido, documento, email, pageable)
     (siempre excluye activo = false)
   - OrdenCompraRepository.buscar(estado, proveedorId, fechaDesde,
     fechaHasta, pageable)
   - OrdenAlquilerRepository.buscar(estado, clienteId, fechaDesde,
     fechaHasta, pageable)

e) openapi.yaml ampliado (los DTO se generan solos al compilar):
   DTOs nuevos: Proveedor, ProveedorCrearRequest, PageProveedor,
   OrdenCompra, OrdenCompraDetalle, OrdenCompraCrearRequest,
   OrdenCompraEstadoRequest, PageOrdenCompra, EstadoOrdenCompra
   (enum), y el campo activo agregado al DTO Cliente.
   Endpoints documentados: /proveedores (CRUD + /buscar) y
   /ordenes-compra (CRUD + /{id}/estado).
   DTOs previos: Cliente, ClienteCrearRequest, ApiError.
   Parametros reutilizables: Pagina (page), TamanoPagina (size),
   IdEnPath (id en path).

4.1 SETRINI - alquiler-eventos-ms-compras
Rol del usuario en el sistema: Encargado de Compras.

CLASES (paquete base sugerido: com.alquilereventos.compras):
- controller/
   ProveedorController      -> endpoints /api/proveedores
   OrdenCompraController    -> endpoints /api/ordenes-compra
- service/
   ProveedorService
   OrdenCompraService       (tambien maneja detalles e historial)
- mapper/
   Mapper<E, D>             (interfaz generica: jerarquia de clases)
   ProveedorMapper
   OrdenCompraMapper
- exception/
   ApiExceptionHandler      (@RestControllerAdvice central)
   RecursoNoEncontradoException   -> 404
   ReglaNegocioException          -> 400
(los repositories YA VIENEN del JAR common: no se duplican)

ENTIDADES QUE USA (todas del JAR):
- Proveedor             -> entidad SIMPLE (CRUD propio)
- OrdenCompra           -> cabecera (CRUD propio)
- OrdenCompraDetalle    -> la asociacion M:N con Equipo (sin controller;
                           la maneja OrdenCompraService con cascade)
- Equipo, Usuario       -> repositorios de APOYO (sin controller)
- OrdenCompraHistorial  -> auditoria de cambios de estado

ENDPOINTS A IMPLEMENTAR:
Proveedores:
  POST   /api/proveedores                              201 / 400
  PUT    /api/proveedores/{id}                         200 / 404
  GET    /api/proveedores/{id}                         200 / 404
  GET    /api/proveedores?page&size                    200 (solo activos)
  GET    /api/proveedores/buscar?nombre=&email=&contacto=&page&size   200
  DELETE /api/proveedores/{id}                         200 / 404
         (borrado logico: activo = false, no borra la fila)

Ordenes de compra:
  POST   /api/ordenes-compra                           201 / 400
         (valida proveedor y equipos, calcula subtotal de cada
          linea y total, estado inicial PENDIENTE, guarda historial)
  PUT    /api/ordenes-compra/{id}                      200 / 400 / 404
         (solo si esta PENDIENTE)
  GET    /api/ordenes-compra/{id}                      200 / 404
  GET    /api/ordenes-compra?estado=&proveedorId=&fechaDesde=&fechaHasta=&page&size   200
  DELETE /api/ordenes-compra/{id}                      200 / 400 / 404
         (borrado logico: estado ANULADA, solo si esta PENDIENTE)
  PUT    /api/ordenes-compra/{id}/estado               200 / 400 / 404
         transiciones validas:
           PENDIENTE  -> CONFIRMADA
           CONFIRMADA -> RECIBIDA   (al recibir: SUMAR stock al equipo)
           PENDIENTE  -> ANULADA    (borrado logico)

REGLAS DE NEGOCIO (logica del service):
- subtotal de cada detalle = cantidad * costoUnitario (lo calcula
  el servidor, el cliente NO lo manda).
- total de la orden = suma de los subtotales.
- no se puede modificar ni anular una orden CONFIRMADA o RECIBIDA.
- al RECIBIR la compra: equipo.stock = equipo.stock + cantidad por
  cada detalle, y registrar el cambio de estado en el historial
  (usa la herencia de HistorialEstado de la entrega 1).
- un proveedor inactivo (activo=false) no puede usarse en ordenes
  nuevas (regla 400).

4.2 TOBI - alquiler-eventos-ms-alquiler
Rol del usuario en el sistema: Encargado de Deposito (y Admin).
Espejo exacto de lo anterior con su dominio:

CLASES (paquete base sugerido: com.alquilereventos.alquiler):
- controller/  ClienteController (/api/clientes),
               OrdenAlquilerController (/api/ordenes-alquiler)
- service/     ClienteService, OrdenAlquilerService
- mapper/      Mapper<E,D>, ClienteMapper, OrdenAlquilerMapper
- exception/   ApiExceptionHandler + las mismas excepciones

ENTIDADES QUE USA (todas del JAR):
- Cliente                -> entidad SIMPLE (CRUD propio)
- OrdenAlquiler          -> cabecera (CRUD propio)
- OrdenAlquilerDetalle   -> la asociacion M:N con Equipo
- ChecklistItem          -> checklist de entrega/devolucion (sin controller)
- Equipo, Usuario        -> repositorios de APOYO
- OrdenAlquilerHistorial -> auditoria (con montoMora)

ENDPOINTS A IMPLEMENTAR:
Clientes:
  POST   /api/clientes                                 201 / 400
  PUT    /api/clientes/{id}                            200 / 404
  GET    /api/clientes/{id}                            200 / 404
  GET    /api/clientes?page&size                       200 (solo activos)
  GET    /api/clientes/buscar?nombre=&apellido=&documento=&email=&page&size   200
  DELETE /api/clientes/{id}                            200 / 404
         (borrado logico: activo = false)

Ordenes de alquiler:
  POST   /api/ordenes-alquiler                         201 / 400
         (valida cliente, stock disponible y fechas; calcula
          subtotal/total; estado inicial RESERVA; historial)
  PUT    /api/ordenes-alquiler/{id}                    200 / 400 / 404
  GET    /api/ordenes-alquiler/{id}                    200 / 404
  GET    /api/ordenes-alquiler?estado=&clienteId=&fechaDesde=&fechaHasta=&page&size   200
  DELETE /api/ordenes-alquiler/{id}                    200 / 400 / 404
         (borrado logico: ANULADA, solo si esta en RESERVA)
  PUT    /api/ordenes-alquiler/{id}/estado             200 / 400 / 404
         transiciones validas:
           RESERVA    -> ENTREGA    (descuenta stock)
           ENTREGA    -> DEVOLUCION (devuelve stock)
           con atraso -> MORA       (calcula montoMora)
           RESERVA    -> ANULADA    (borrado logico)

REGLAS DE NEGOCIO:
- no alquilar mas stock del disponible (regla 400).
- subtotal = cantidad * precioDia * dias del alquiler.
- un cliente inactivo no puede usarse en ordenes nuevas.
- todo cambio de estado queda en OrdenAlquilerHistorial.

SECCION 5 - PASO A PASO PARA ARMAR EL MICROSERVICIO
====================================================================
(Mismo procedimiento para los dos; solo cambia el dominio)

PASO 1. Clonar tu repo y crear el proyecto
  git clone https://github.com/alquiler-eventos-org/alquiler-eventos-ms-compras.git
  (o ms-alquiler para Tobi)
  Crear el proyecto con Spring Initializr (start.spring.io) o a mano:
  - Maven, Java 21, Spring Boot 3.4.5
  - Dependencias: Spring Web, Spring Data JPA, Validation,
    PostgreSQL Driver, Lombok
  - Agregar springdoc-openapi-starter-webmvc-ui 2.6.0
  Agregar en el pom la dependencia del JAR comun:
    <dependency>
      <groupId>com.alquilereventos</groupId>
      <artifactId>alquiler-eventos-common</artifactId>
      <version>1.0.0-SNAPSHOT</version>
    </dependency>
  (requiere haber corrido "mvn clean install" en common antes)

PASO 2. application.yml 100% configurable (nada de valores quemados)
  spring:
    datasource:
      url: ${DB_URL}
      username: ${DB_USER}
      password: ${DB_PASSWORD}
      driver-class-name: org.postgresql.Driver
    jpa:
      hibernate:
        ddl-auto: validate
    liquibase:
      change-log: classpath:db/changelog/db.changelog-master.yaml
  server:
    port: ${SERVER_PORT:8082}          # 8081 para Tobi
    servlet:
      context-path: ${API_CONTEXT_PATH:/api}
  app:
    pagination:
      default-page-size: ${DEFAULT_PAGE_SIZE:10}
  logging:
    config: ${LOGGING_CONFIG:classpath:logback-spring.xml}
  springdoc:
    swagger-ui:
      path: /swagger-ui.html
  Las credenciales reales van en variables de entorno (o en un .env
  local ignorado por git, NUNCA commiteado).

PASO 3. Verificar arranque contra Supabase
  Correr la app: Liquibase aplica los changeSets pendientes (17 y 18
  en la primera corrida) e Hibernate valida las 16 entidades.
  Si arranca sin errores, la base queda lista y validada.

PASO 4. Capas por entidad (orden recomendado de codigo)
  1) mapper: interfaz generica Mapper<E, D> con toDto(E) y toEntity(D)
  2) service: interfaz + implementacion @Service
  3) controller: @RestController que SOLO delega al service
  4) exception: ApiExceptionHandler con @RestControllerAdvice
  Regla de oro: Controller -> Service -> Repository, sin saltos.

PASO 5. Entidad simple primero (Proveedor o Cliente): CRUD completo
  con paginacion, filtros (usar los metodos buscar() del JAR) y
  borrado logico. Probar todo por Swagger.

PASO 6. Entidad principal (OrdenCompra o OrdenAlquiler): crear con
  detalles (la M:N con cascade + orphanRemoval), filtros + paginado
  con buscar() del JAR, cambio de estado con historial y borrado
  logico ANULADA.

PASO 7. Logs a disco (logback-spring.xml)
  - Appender de archivo con rolling diario + ruta configurable
    (ej. ${LOG_DIR:./logs}) + appender de consola para desarrollo.
  - INFO para controller y service, DEBUG para el SQL:
    logging.level.org.hibernate.SQL: DEBUG (configurable).

PASO 8. README + pruebas finales
  - Documentar variables de entorno y como correr.
  - Probar TODOS los endpoints por Swagger verificando codigos
    200 / 201 / 400 / 404.
